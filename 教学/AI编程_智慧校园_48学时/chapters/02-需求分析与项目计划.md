# 第02章 需求分析与项目计划

状态：`DESIGNED`。课内 4 学时，按 1＋2＋1 分配。以下实验是拟定课堂活动，验收结果待学生实际完成后记录。

## 进入条件与学习目标

已有第01章功能卡和 AI 协作记录。教师须准备脱敏的产品演示、需求模板和完整性检查样例，均为待制作资源。

学生完成后能区分业务需要与技术方案；能把用户故事转成可观察验收条件；能按依赖划分最小可交付版本；能解释三个角色的边界，以及为什么 AIRIOT 和 UI 复刻不应阻塞必修主线。

## 模块一：确定用户、问题与范围（1 学时）

需求不是页面名称清单。“设备管理页面”没有说明用户要做什么；“查看者按空间筛选设备，并看出未知通信状态”才有可验证目标。每组用“作为谁，希望做什么，以便解决什么问题”写用户故事，再把实现方式留到设计阶段。

共同角色为 ADMIN、CAMPUS_MANAGER、CAMPUS_VIEWER。管理员可管理与分派；管理人员只处理分派给本人的事件；查看者只读。角色权限最终由后端执行，隐藏按钮只改善使用体验。普通学生是系统开发者，不因此自动成为运行系统的管理员。

必修范围为模拟空间设备、监测历史、角色权限、本地演练事件、设备责任与审计。明确排除真实远端控制、外部通知、真实学生个人信息和费用节能率推算。AIRIOT 适配保留为进阶入口，界面允许自主设计。

产出：角色表、范围表与不少于六条用户故事。

## 模块二：写验收条件并拆分版本（2 学时）

用“给定前提—执行动作—观察结果”写验收。例：给定设备 `online=null`，当查看台账时，显示“未知”，不能显示“离线”。再补接口失败、空列表、加载中等异常路径，避免只有演示成功路径。

事件故事必须保留完整门槛：创建本地 DEMO 事件，分派后开始处理，保存处置记录，由管理员模拟恢复，处理者独立请求核实，核实通过并填写结论后关闭。来源状态和处置状态是两条不同事实，恢复不能自动关闭。旧版本提交返回 409，先回读再由人重新决定。

按总纲统一的五个里程碑拆分：M1 定义项目；M2 设备可见；M3 数据可信；M4 业务闭环；M5 可交付。每张任务卡写目标、前置依赖、交付物、验收人、预计工作量和风险。工作量先用小/中/大表达并通过课堂实际记录校准，不让 AI 编造精确工期。

将第01—03章归入 M1，第04—06章归入 M2，第07—08章归入 M3，第09—10章归入 M4，第11—12章归入 M5。48 学时是教学总量，不等于企业完整系统生产开发工期。课外选做不得成为基础验收的必需条件。

产出：需求编号表、验收清单、五阶段任务板和风险表。

## 模块三：需求评审与变更控制（1 学时）

另一组扮演使用者，挑选三条需求逐字询问“怎样看到它完成”。对模糊词“友好、实时、安全、完整”补具体判断，例如“请求失败保留最后成功数据和时间”。尚未确定的刷新间隔标为待设计，不能随意写成零延迟。

模拟新增“手机通知”要求：记录提出原因、影响的接口与权限、工作量和取舍。本课程基础范围不含外部通知，学生应保留变更记录并说明不纳入本轮，而非顺手接入真实发送服务。

产出：评审意见、修订后的需求基线和一条被接受或延期的变更记录。

## 最小实验步骤

1. 选设备台账、事件关闭、责任登记三个场景，分别写用户故事。
2. 为每个故事写一个成功场景和两个失败或边界场景。
3. 请 AI 找歧义，人工回查课程共同约定后修订。
4. 给需求编号，并连接“需求→任务→验收证据”的关系。
5. 演练一次范围变更，留下决定、理由和受影响条目。

## 人工检查点与验收

需求编号由本组统一管理。AI 建议必须映射到已有范围，不能以回答里出现的新功能自动扩充作业。

| 验收项 | 预期证据 |
| --- | --- |
| 角色清楚 | 三角色表含本人事件限制和后端授权要求 |
| 范围可控 | 必修、选做、不做三类条目及理由 |
| 验收可执行 | 三个场景各有成功、失败、边界条件 |
| 任务有依赖 | 五阶段任务板能解释前后顺序 |
| 变更可追踪 | 一条变更的影响、决定及需求编号 |
| 总量一致 | 12章×4学时=48学时，AIRIOT选做不挤占必修 |

## 典型错误及定位

- 写“所有人能处理事件”：回查角色表，补管理人员本人范围及查看者拒绝路径。
- 用“做成原界面一样”作为验收：回查用户目标，改为字段、状态、可用性检查。
- 任务板只有“前端、后端”：任务过大，按可见业务结果继续拆分。
- 关闭流程省掉核实：对照关闭条件，分别写来源恢复与独立核实，不能合并。
