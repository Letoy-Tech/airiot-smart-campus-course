## 第一步：制造一个能恢复的小故障，并留下三个观察

现在只练“成功条件写反”的定位，不改数据库，不改权限。

### 1. 保存修改前的一小段代码

在 VS Code 左边打开 `frontend/src/api/campus.ts`。按 Windows `Ctrl+F` / macOS `Command+F`，查找 `extractFirstRead`。它把后端回信里的设备列表和观察时间拿出来。教师参考逻辑如下；如果你的写法不同，先把实际函数复制到 `evidence/ch11.md` 的“修改前”，请教师指出等价的成功/失败分支，再只改那个条件，不强行整文件覆盖。

```typescript
export function extractFirstRead(response: ApiEnvelope & { data: ReadResult<Device> }): ReadResult<Device> {
  // STUDENT_TODO_A_BEGIN：检查业务 code，再解包同一批列表与观察时间。
  if (response.code !== 0) throw new ApiError('设备读取未成功，请核对业务响应。', 200, response.code)
  return { items: response.data.items, observedAt: response.data.observedAt }
  // STUDENT_TODO_A_END
}
```

`!==` 表示“不等于”。合同规定 `code=0` 才是业务成功，因此原句是“不是0就拒绝”。为了本次练习，**只把这个条件的 `!==` 改为 `===`**，变成下面这一行，然后保存文件：

```typescript
if (response.code === 0) throw new ApiError('设备读取未成功，请核对业务响应。', 200, response.code)
```

这是故意制造的错误，不是建议的实现。不要改 `getDevices`、请求路径、其余判断或测试。先在 `ch11.md` 写：“本轮人为把成功条件写反；预计正常设备响应会被前端拒绝。”

### 2. 打开浏览器的 Network，看请求有没有成功

下面以 Chrome/Edge 为例。页面右键 →“检查”，打开开发者工具；点击顶部“Network / 网络”。看不到时点击顶部 `»` 展开。保持录制圆点亮着，点击“Fetch/XHR”筛选，再刷新浏览器页面。不是点击“触发演练”，这一轮没有业务写入。

在过滤框输入 `devices`，点击名为 `devices` 的请求：

1. 在“Headers / 标头”的 **General / 常规** 区读 `Request URL` 和 `Status Code`。预期路径是 `/api/campus/devices`，状态200。
2. 点“Response / 响应”，找到最外层 `code`，预期为0；再展开 `data`，应有 `items` 和 `observedAt`。只记录字段、数量和一个模拟ID，不必复制16台设备全文。
3. 看页面。故障条件下，页面会显示“设备读取未成功，请核对业务响应。”一类失败提示。页面此前已有成功快照时，可能保留旧数据并提示刷新失败；这是失败反馈，不是这次读取已成功。

**200只表示这次HTTP请求成功返回；code=0才表示业务成功。两者都成功而页面拒绝，优先检查前端收到回信之后的判断。** 不要因为页面报错就重建数据库。

不要复制 Request Headers 里的 Cookie，不要点“Copy as cURL”，不要导出HAR文件。这些内容可能携带登录信息。只手工记录常规区的路径/状态和已核对的模拟业务字段。

## 第四步：先预测，再逐字段读真实MySQL报告

“并发”是两个人几乎同时修改同一条记录；“事务回滚”是一次修改中途失败后，已做的改动一并撤销。普通函数测试不能证明数据库真的锁住了同一条记录。

### 1. 学生先填四个预测，教师再运行

打开 `docs/ch11-assertions.md`，先填写四组预测：

| 场景名 | 用白话写出预测 |

| owner_concurrent_update | 两位管理员拿同一责任版本修改，只有一人成功；另一人409；责任版本和历史只增加一次，旧事件不换人 |
| event_concurrent_notes | 两个合法请求用事件同一版本加记录，一成功一409；版本加1，时间线只加1 |

### 2. 打开报告，按键名找事实

在 VS Code 打开报告，按查找搜索 `event_timeline_rollback`。先看顶层 `recordedAt`、`javaVersion`、`mysqlVersion`、`database`，核对是不是教师刚提供的那次执行。场景在 `scenarios` 数组中，顺序可能变化，按 `scenario` 名称找，不按第几项猜。

下面是作者现有 **2026-10-18T18:48:38.097852Z 历史报告**中事件回滚的字段，原报告记录Java17.0.6、MySQL8.4.10、库 `campus_course_test`。这不是你今天的结果：

```json
{
  "scenario": "event_timeline_rollback",
  "objectId": "cb50292f-7761-4977-9b3f-1c3e5c21b3da",
  "httpStatus": 500,
  "faultHit": true,
  "rowsAffectedBeforeFault": 1,
```

逐行读法如下。只看500不能证明回滚；500也可能发生在更新之前。

| 报告字段 | 这个样例说明什么 | 本人报告怎么核对 |
| --- | --- | --- |
| objectId | 本次故障属于哪条事件 | 与同一场景测试关联，不要求你的ID相同 |
| rowsAffectedBeforeFault=1 | 主行UPDATE确实命中一条 | 不能是0或缺失 |
| versionObservedInsideTransaction=8 | 事务内部已经从7改到8 | 比故障前版本多1 |
| faultHit=true、httpStatus=500 | 预定故障命中，写操作失败 | 400/403/409提前拒绝不算此实验 |
| before=32、fault=25、after=33 | 前后回读不是故障事务的同一连接 | 连接号应相互区分，不要求等于示例数字 |
| versionBefore=7、versionAfterFailure=7 | 已更新的版本没有留下 | 前后相等 |
| timelineBefore=7、timelineAfterFailure=7 | 失败没留下半条历史 | 前后相等 |
| 两个SnapshotUnchanged=true | 主行和时间线完整快照一致 | 不只比较数量 |
| normalControl为200/8/8 | 清除故障后，同对象同版本能正常提交 | 证明请求本身合法，且正常时版本/时间线都加1 |

再用同一份历史报告核对另外三组。下面是字段摘录，不能拿这些数值覆盖本人的报告：

| scenario | 历史报告中的实际字段 | 合同判断 |
| --- | --- | --- |
| event_concurrent_notes | statuses=[409,200]；mysqlConnections=[25,26]；versionBefore=7；versionAfter=8；timelineAdded=1 | 两种结果各一、两连接、版本与历史各加1；数组顺序可以反过来 |
| owner_concurrent_update | statuses=[409,200]；mysqlConnections=[25,26]；versionAfter=1；timelineAdded=1；priorEventUnchanged=true | 此用例起始expectedVersion=0；更新后1，旧事件完整不变 |
| owner_timeline_rollback | objectId=teaching_env_01；httpStatus=500；faultHit=true；rowsAffectedBeforeFault=1；事务内版本1；故障前/后版本0/0、历史0/0；两个SnapshotUnchanged=true | 主行确实改过，回滚后责任与历史都回到基线 |
| owner_timeline_rollback 的连接与正常对照 | fault=25、before=29、after=30、normalControlRead=31；normalControl为200/版本1/历史1 | 独立连接回读，清除故障后正常提交成立 |

责任并发报告没有 `versionBefore` 字段，不要让 AI 补造。要核对起始0，在 VS Code 打开 `backend/src/test/java/edu/campus/course/TeacherDbTest.java`，搜索 `concurrentOwnersUseTwoConnectionsAndKeepExistingEvent`，看两个请求体的 `expectedVersion:0`；搜索 `CyclicBarrier(2)` 和 `barrier.await`，理解两个请求先一起就绪才争同一条记录。只读这几个位置，不要求重写线程代码。
