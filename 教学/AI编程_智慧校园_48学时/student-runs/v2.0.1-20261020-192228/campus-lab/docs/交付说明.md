## 1. 作品有哪些页面

九个菜单都在 `frontend/app.js` 里，地址用 `#` 片段切换（例如 `#history?deviceId=d05&tagId=power`）。页面本身只负责显示，所有取数都走 `frontend/data-service.js`。

| 页面 | 用来做什么 | 连接后端时的数据来源 |
| --- | --- | --- |
| 概览 dashboard | 看设备/空间/点位总数、当前读数与状态 | `GET /api/overview` |
| 设备 devices | 设备列表、筛选、打开详情看点位与负责人 | `GET /api/devices`、`GET /api/spaces`、`GET /api/owners`、`GET /api/overview` |
| 空间 spaces | 改楼栋/楼层并保存（ADMIN） | `GET /api/spaces`、`PUT /api/spaces/{id}` |
| 能源 energy | 设备功率/电压横向比较与历史曲线 | `GET /api/overview` |
| 历史 history | 某设备某点位的历史曲线与样本表 | `GET /api/overview` 里的 `history` |
| 原始报警 alarms | 查原始报警字段、跳设备详情（只读） | `GET /api/overview` 里的 `alarms` |
| 演练事件 cases | 建事件、分派、开始、记事、恢复、核实、关闭与时间线 | `GET /api/cases`、`POST /api/cases`、`POST /api/cases/{id}/actions` |
| 设备责任 owners | 给设备登记负责人与备注（带版本号防覆盖） | `GET /api/owners`、`PUT /api/owners/{deviceId}` |
| 管理 admin | 接入状态（固定教学模拟）与审计列表（仅 ADMIN） | `GET /api/integration`、`GET /api/audit` |

页面还有两种数据方式：页面顶部选“连接后端”才读 MySQL；选“浏览器演示”只读 `materials/mock-campus.json`，不写数据库，也不显示演练与审计。

## 2. 从空页面到前端，再到后端

**第一阶段（第 01–02 课）：先有页面，再让页面有数据。**
第 01 课只有一张空壳页面和几个菜单；第 02 课做设备台账与筛选。这一阶段的数据全部来自 `materials/mock-campus.json`，页面没有保存能力，改不了任何东西。

**第二阶段（第 03–06 课）：让页面“像能用”，但只存在浏览器里。**
第 03 课做空间与责任，第 04 课处理读数（明确“0 是有效值、缺失不补 0”），第 05 课做历史与原始报警，第 06 课把九个菜单逐项写清“显示什么 / 从哪里读 / 会保存什么 / 哪些必须后端校验”。**这一阶段并不是刷新就回样本**：空间、责任和演练事件当时靠 `localStorage` 里的 `campus-v2-demo` 持久化，刷新或重开标签还能看到改动。当时页面上**已经有角色检查（演示身份）和本地审计记录**，但那是前端的按钮/分支判断加浏览器本地日志，**不代表后端权限，也不是数据库审计**——绕过页面直接发请求没人拦。直到第 11 课 11-06，才把 `campus-v2-demo` 的旧业务读写清理掉，此后浏览器只保留数据方式偏好（`campus-v2-data-mode`），权限与审计全部由后端负责。

**第三阶段（第 08–11 课）：加后端，一课一版迁移，逐页换真数据。**
后端是 Spring Boot 3.4.2 + Java 17；Flyway 按课次推进：**V1 在第 08 课、V2 在第 09 课、V3 在第 10 课、V4 在第 11 课**，不是一次性在开头建完——V1 先把设备、空间、点位这些基础数据从教学样本灌进库，之后每课再补当课需要的表与约束。账号口令在库里只存 BCrypt 摘要；登录用 `POST /api/login` 换令牌，令牌放 Redis，业务记录一律进 MySQL。第 10 课空间与责任接后端（保存后前端独立 GET 回读，刷新重新登录仍一致），第 11 课演练事件与审计接后端（每步动作带 `expectedVersion`，冲突返回 409 且只回读、不自动重发）并清掉旧的本地业务数据。前端在 `data-service.js` 里把请求集中到一处，`tools/serve.mjs` 只公开 `frontend/` 并把 `/api/*` 转发到 `127.0.0.1:8098`。

**第四阶段（第 12 课）：换目录重跑一遍。**
把同一份工程复制到新目录 `campus-lab-handoff`，用独立项目名 `campus-v2-handoff` 起新容器、新卷、新口令，在本机把九个菜单重新走了一遍。本次新事件是 `case-a4b66d456baa`：自动分派给 `manager`，一路走到 **CLOSED v6、时间线 6 条**，ADMIN 读到 **审计 8 条**——与 `docs/本组实做记录.md` 第 12 课一节逐条对应。

**收尾时我改的一处页面文字**：设备页顶部原本写“负责人仍是浏览器演示”，但实际已经调用 `GET /api/owners`，详情来源段也写责任来自 MySQL。修正后统一为“点位读数从 `/api/overview`、负责人从 `/api/owners` 读取，均来自本机 MySQL”；只改了文字与注释，接口调用和权限判断没动。

## 3. MySQL 保存什么，Redis 保存什么

**MySQL（课程库 `campus_course`，本机容器；Flyway V1–V4 分别在第 08、09、10、11 课加入）保存业务记录：**

- 账号 `users`（用户名、BCrypt 摘要、角色、是否启用）
- 空间 `spaces`、设备 `devices`、点位 `points`
- 历史样本 `history_samples`、原始报警 `alarms`
- 设备责任 `owners`（负责人、备注、版本号、更新时间）
- 演练事件 `cases` 与时间线 `case_timeline`
- 审计 `audit`（每次成功保存/动作同事务写一条）

这些记录刷新页面、重启后端、重启 Redis 都还在。空间、责任、事件、审计的写入都是“先改库、同事务记审计”，失败就不留半条。

**Redis 只保存“你现在是谁”的短期凭条：** `campus:v2:session:<token>` → `{username, role}`，有效期 1800 秒；退出登录就删键。本课程 Redis 关闭了 `--save` 与 `--appendonly`，所以重启 Redis 后所有会话立即失效，需要重新登录，但 MySQL 的业务数据一条不丢。

**浏览器里现在只有两样东西：** 登录令牌放在 `data-service.js` 的内存变量里（刷新即丢，这是“刷新要重新登录”的原因）；`localStorage` 只记数据方式偏好 `campus-v2-data-mode`（`backend` / `demo`），不存身份、不存业务数据。（第 03–06 课曾用 `campus-v2-demo` 在浏览器里存空间、责任与演练事件，第 11 课 11-06 已移除，过程见第 2 节。）

## 4. 我修过的一个真问题：新目录启动被容器名占用

**现象**：新目录 `.env` 生成后，我执行 `docker compose -p campus-v2-handoff up -d`。新网络和新卷都建好了，但创建容器阶段报错：

```
Conflict. The container name "/campus-v2-mysql" is already in use by container ...
```

**判断**：旧项目的 `compose.yaml` 里写死了 `container_name: campus-v2-mysql` / `campus-v2-redis`，而 Docker 的容器名全机唯一；旧容器只是 `stop` 了，名字还占着，所以新项目抢不到这个名字，尽管新项目名、新卷、新网络都是独立的。

**处理**：按课程约定的“只停不删”，先停住新项目，旧容器、旧卷、旧 `.env` 一个都没动，也没有 `down -v`。然后只改本目录 `compose.yaml`：删掉 mysql 与 redis 各自那一行 `container_name`，其余（顶层 `name`、回环端口 23501/23502、`mysql-data` 卷声明、镜像、认证、healthcheck、Redis 关持久化）全部保持原样。改完**直接重跑同一条** `docker compose -p campus-v2-handoff up -d`，复用了上次已建的网络与卷，两个容器起来后都是 `healthy`。

**结果与证据**：新容器名是 `campus-v2-handoff-mysql-1` / `campus-v2-handoff-redis-1`；旧容器仍叫 `campus-v2-mysql` / `campus-v2-redis` 并保持 `Exited`，没改名也没重建；新卷 `campus-v2-handoff_mysql-data` 创建于 `2026-10-20T20:47:14Z`，旧卷 `campus-v2_mysql-data` 仍为 `2026-10-20T15:52:09Z`。时间戳没变**只说明旧卷没有被重建**；本轮没有重新启动旧库逐条回读业务数据，所以这不能当成“旧数据完整”的验证。

**学到的**：容器名和项目名是两套东西。项目名决定卷和网络的前缀，`container_name` 却会写死一个全机唯一的名字，一旦写死，就失去了“换项目名即隔离”的效果。

## 5. 怎么安装、启动、停止

**装什么**：Node.js 22（页面静态服务）、JDK 17（后端）、Docker Desktop（能跑 `docker compose`）。版本不对只在当前终端窗口临时切换，不改系统环境变量。

**第一次准备（工作目录 `campus-lab-handoff/`）**

```sh
node tools/setup-env.mjs
```

它生成本机随机口令到根目录 `.env`，**不会在屏幕显示口令**。已有 `.env` 时只提示保留、以非 0 退出码结束，这是正常的：不要重新生成，也不要拿新口令去连旧卷。

**启动（三个窗口，目录都写清）**

```sh
# C 窗口：容器（必须带 -p）
# 工作目录：campus-lab-handoff/
docker compose -p campus-v2-handoff up -d
docker compose -p campus-v2-handoff ps        # mysql、redis 都 healthy 再做下一步

# B 窗口：后端
# 工作目录：campus-lab-handoff/backend/
java -version                                  # 必须是 17
sh ./mvnw spring-boot:run

# A 窗口：页面
# 工作目录：campus-lab-handoff/
node tools/serve.mjs                           # 浏览器打开 http://127.0.0.1:5188
```

**确认起来了**：`curl http://127.0.0.1:8098/api/health` 返回 `code=0`、`data.status=UP`；页面顶部选“连接后端”，用本机 `.env` 里的演示账号登录（口令只在本机查看，不写进任何文档）。

**停止**

```sh
# A、B 窗口各自 Ctrl+C
# 工作目录：campus-lab-handoff/
docker compose -p campus-v2-handoff stop
docker compose -p campus-v2-handoff ps -a     # 两个容器显示 exited 即停好
```

`stop` 只停容器，容器、卷、MySQL 数据全部保留。**不要 `docker compose down -v`、不要删卷、不要删或改名旧容器。**

**本次实际收尾（2026-10-21，已完成）**：原 C 执行 `node tools/export-source.mjs --out .runtime/hand-in-final/campus-lab`，得到 **141 个公开文件**和新的 `SHA256SUMS.txt`；**141 项逐个哈希与原工程源码、新目录运行副本全部一致**，最终导出里的两份说明也已打开核对，旧导出（v1…v4）保留未覆盖。停机按上面步骤做：新 A、新 B 各自 `Ctrl+C`（后端日志显示连接池与 Tomcat 正常关闭）；新 C `docker compose -p campus-v2-handoff stop` 后 `ps -a`，**两新容器 `Exited(0)`，两旧 `campus-v2` 容器也保持 `Exited(0)`**。新旧两个 MySQL 卷、两个 `.env` 都保留，没有 `down`、没有删卷或删容器。若之后还要同步收尾文字，仍用**未使用过的新输出名**重新导出重核，不手改历史 SHA 清单。

**换回旧环境（本轮尚未演练，只是步骤）**：先在新目录 `stop`，再到旧目录 `campus-lab/` 执行 `docker compose -p campus-v2 up -d`，用旧 `.env` 登录。两套环境的宿主端口完全一样（5188 / 8098 / 23501 / 23502），所以**只能一组在跑**，切换只 `stop` 不 `down`。注意：旧容器现在仍叫 `campus-v2-mysql` / `campus-v2-redis`，但如果旧目录也同步了“去掉 `container_name`”的写法，重跑时 Compose 可能重建容器并改用带序号的默认名，也可能沿用原容器——以实际 `docker compose -p campus-v2 ps -a` 为准，旧数据是否原样也要回读确认，不能预先断言。
