# 第10段：设备责任变了，旧事件归谁

先看一个生活例子：今天把值班责任从A交给B，不代表昨天已经交给A处理的事情自动转给B。本段把这个区别写进程序，并用两条真实本地事件验证。

继续桌面 `campus-ai-lab/app` 和本组 `teacher-db`。我们只补责任版本检查的一行代码；教师已提供责任表、候选人检查、事务、保存历史和页面。“版本”是记录每次有效修改后的编号；提交旧版本必须拒绝，不能覆盖别人刚保存的结果。

## 第4步：登记A，创建一条已经开始处理的旧事件E1

打开 `http://127.0.0.1:5178/#owners`，按第08段流程用admin登录。重启后端后需要重新登录；密码从本机教师账号资料取得，不发AI。

1. 点顶部 **“责任登记”**。在 **“设备责任台账”** 找带编号 `teaching_env_01` 的行并点击。详情显示当前责任人、版本和 **“责任变更时间线”**。
2. 先记当前值。首次未登记可能是v0、当前责任人未登记；已有记录就使用实际值，不清库。
3. 在 **“登记新的责任人”** 下，“责任人”选 **“管理人员 A（manager-a）”**；“变更理由”填 `第10段：由A负责后续温度巡查`；点 **“提交责任变更”**。
4. 等出现 **“责任登记已确认；已有事件的分派保持不变。”**，点 **“刷新登记”**，再选该设备。应看到A、更新后的版本和包含本次理由的时间线。只重复读取，不再点提交。
5. 点 **“事件工作台”**，场景选“温度巡查”，点一次“触发本地演练”。记实际ID为E1，确认已经自动分派给A、状态“已分派”。
6. 点右上“退出 / 切换身份”，等登录表单，再用manager-a登录。打开“事件工作台”，按E1实际ID找到该行；在“处理记录 / 分派说明”填 `第10段：A开始处理E1`，点 **“开始处理”**。确认变“处理中”。暂不追加NOTE、不关闭。

## 第5步：仅改设备责任为B，比较E1，再创建E2

1. 退出manager-a并登录admin。点“责任登记”，重新选择 `teaching_env_01`，让页面读到当前责任版本。
2. “责任人”改选 **“管理人员 B（manager-b）”**；“变更理由”填 `第10段：后续新事件改由B负责，旧事件保持原分派`；点“提交责任变更”。成功后刷新登记并重新选设备，确认B和新增责任时间线。
3. **这时不要操作E1。** 在Console重新执行第4步的读取代码，输入同一个E1实际ID。把结果存为“责任改B后E1”。与上一份逐项比较：`assigneeUid`仍A、`state`仍IN_PROGRESS、`version`不变、`timeline`内容不变。仅看“名字还是A”不够。
4. 点“事件工作台”，再触发一次“温度巡查”，将新的实际ID记作E2。它应自动分派给B、状态已分派。E1和E2必须是两个不同ID。

本步不改源代码。证据表应能看出：设备当前owner=B，E1 assignee=A，E2 assignee=B。`owner`是设备当前责任，`assignee`是某条事件自己保存的负责人。

## 第6步：B虽然是现任责任人，也不能给A的E1加记录

先保留第5步“E1未变”的证据，再做这个会产生新动作的对照，不能混在一起。

1. 退出admin，用manager-b登录，点“事件工作台”，按ID打开E1。应仍显示A，B没有处理它的入口；不要选“仅分派给我”，否则会把E1筛掉。
2. 打开Console，回[第05段第5步](05-后端空间与设备接口.md)，重新复制并执行第一个代码框中完整的 `courseWrite` 定义。然后执行：

```js
var e1Id10 = prompt('粘贴仍归A、状态IN_PROGRESS的E1实际ID');
if (!e1Id10) throw new Error('没有ID，停止');
var e1Path10 = '/api/campus/alarm-cases/'+encodeURIComponent(e1Id10);
var beforeB10 = await fetch(e1Path10,{credentials:'same-origin'}).then(r=>r.json());
if (beforeB10.code!==0 || beforeB10.data.state!=='IN_PROGRESS' ||
    beforeB10.data.assigneeUid!=='manager-a') throw new Error('前提不符，先核对E1');
var deniedB10 = await courseWrite(e1Path10+'/notes','POST',{
  note:'第10段本人范围对照',expectedVersion:beforeB10.data.version
});
var afterB10 = await fetch(e1Path10,{credentials:'same-origin'}).then(r=>r.json());
console.log({id:e1Id10,status:deniedB10.status,message:deniedB10.message,
  readSucceeded:afterB10.code===0,
  unchanged:JSON.stringify(beforeB10.data)===JSON.stringify(afterB10.data)});
```

预期403/ACCESS_DENIED，前后详情不变。若是401、CSRF相关错误或409，先核对会话、事件状态与版本，不能算本人范围拒绝。

3. 退出B并用manager-a登录，再打开E1。应有 **“处理记录 / 分派说明”**；填同一句 `第10段本人范围对照`，点 **“提交处理记录”**。应成功，仍处理中，版本和时间线各前进一次。刷新后核对NOTE仍存在。

这次E1变化来自A刚追加的NOTE，不是设备责任变更。将B拒绝和A成功分别保存，身份、版本、说明都写清。

## 第7步：两个标签页制造旧版本，亲自看409如何保留输入

这一步用**同一个admin身份**的两个标签，不用它们模拟A/B。旧版本是“我还拿着上一版资料提交”，不同于下一段才做的真实数据库并发。

1. 退出A，登录admin，打开“责任登记”，选择 `teaching_env_01`，确认当前责任为B。右键浏览器标签选择“复制标签页／Duplicate”；两个标签都打开 `http://127.0.0.1:5178/#owners` 并选同一设备，确认两边显示相同版本n。
2. 第一标签选A，理由填 `第10段第一标签：交给A`。第二标签选B，理由填 `第10段第二标签：我仍准备交给B`。先都不要提交。
3. 只在第一标签点“提交责任变更”，等成功；它应显示A和n+1。**不要刷新第二标签，不点击别的设备。**
4. 回第二标签点“提交责任变更”。应显示 **“409：责任记录已变化，原输入已保留。”** 随后显示 **“最新责任与时间线已回读，请重新判断。”**。检查第二标签原来的B选择和理由仍在，但最新责任已经是A。
5. 点 **“已核对最新责任”** 只是确认你看过最新记录，不会自动再次提交。为避免额外改写，本次停在这里，不再点“提交责任变更”。

若回读失败，页面应出现“重试回读”；先恢复读取再点它，不可把未回读当冲突已经解决。若两边都成功，先核对第二页是否在提交前意外刷新过版本，再检查C10调用，不盲目增加版本。

本步不改代码。把两个版本、第一标签成功、第二标签409、输入保留与最新责任回读写入 `evidence/ch10.md`。截图只截业务区域。
