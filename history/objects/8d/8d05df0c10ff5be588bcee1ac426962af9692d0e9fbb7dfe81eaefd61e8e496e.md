## 模块一：设计可追溯的责任关系（1 学时）

设备当前责任是一个会变化的关系，事件负责人是在具体事件中作出的分派决定。二者不能用一个动态关联查询代替，否则更换设备责任人会悄悄改变旧事件的负责人。

责任主记录使用 `deviceId/ownerUid/ownerName/version/updatedAt`；首次未配置时 owner 与时间为 null、版本为 0。历史记录保存前后责任人、说明、操作者、时间和对应版本。不要覆盖旧历史，也不要把姓名当作稳定身份标识。

| 对象 | 可变化内容 | 必须保留的事实 |
| --- | --- | --- |
| 设备责任主记录 | 当前责任人、版本 | 设备标识 |
| 责任变更时间线 | 只追加 | 前后人员、原因、操作者和时间 |
| 已有事件 | 通过明确的事件指派动作改变 | 原负责人及原事件时间线 |

本章的审计重点是责任与事件时间线。原系统 `/campus/audit` 主要记录模拟开关操作，不能拿它冒充责任变更查询；教学主线不开启开关控制。

产出：三对象关系图和责任变更规则清单。

## 模块二：登记责任并验证自动分派（2 学时）

沿用 `GET /campus/device-owners`、`GET /campus/device-owners/{deviceId}`、`PUT /campus/device-owners/{deviceId}`。写请求只含 `ownerUid/note/expectedVersion`；仅管理员可写，候选人员须为当前启用、未锁定且有有效处理角色的账户。不接受 null 清空责任人。

服务端在事务中检查设备范围和人员资格、锁定责任行、比对版本，更新主记录并追加历史。初次写传 0；旧版本返回 HTTP 409 `VERSION_CONFLICT`。详情按版本与 id 排序；操作者从当前登录身份取得，客户端上传 `actorUid`、时间等额外字段应被拒绝。

最小实验：

1. 选择独立教学夹具中的 `teaching_env_01`，读取未配置责任行，确认 owner 为 null、version 为 0；教学温度巡查场景也引用该设备。
2. 管理员登记 A，填写原因；刷新详情，核对版本为 1、历史包含从 null 到 A 的变化。
3. 触发事件 E1，确认系统在创建时检查 A 的当前资格并自动分派给 A。
4. 管理员把设备责任改为 B，回读责任详情；E1 的负责人和历史应保持原样。
5. 触发 E2，确认新事件分派给 B。只有明确调用 E1 的指派接口才可改变 E1，不能后台批量联动。
6. 通过教师准备的账户状态夹具使 B 不再具备有效处理资格；再次创建事件应保持未分派，并在创建时间线说明原因。不得把旧缓存中的 B 当作有效候选人。
7. 用过期版本更改责任，核对冲突提示和保留输入；用查看者直接发写请求，应得到 403。

产出：责任列表/详情页、责任服务及 E1/E2 对照证据。账户状态夹具仅面向隔离教学账户，其准备方式须由教师在资源制作阶段固定。

## 模块三：从历史记录重建操作过程（1 学时）

同桌只拿脱敏时间线，回答：谁做了什么、改变前后是什么、当时属于哪个版本、为什么 E1 仍归 A。作者再用真实详情解释结果。

人工检查时间线是否由数据库回读，页面是否把当前姓名错误覆盖到全部历史；确认普通校园角色可以读取合同允许的责任记录，但不能因此获得管理权限。界面隐藏写按钮之外，仍要验证直接请求被拒绝。

产出：一页责任追溯报告，以及“当前值”与“历史事实”的截图标注。

## 典型问题、巩固与接力

改责任后旧事件也变了：检查是否用设备 owner 动态代替事件 assignee，或存在批量更新语句。首次登记冲突：核对未配置记录的版本是否为 0，而非自行改成 1。历史显示全部为 B：检查返回的是历史保存值还是当前主记录值。人员已禁用仍被分派：定位后端资格检查及缓存，不只刷新下拉框。

课后绘制“责任主记录—责任历史—事件—事件历史”关系图，说明各表存在的原因。进阶可增加只读历史筛选与分页；新增字段先改合同，不要求制作统一审计平台。
