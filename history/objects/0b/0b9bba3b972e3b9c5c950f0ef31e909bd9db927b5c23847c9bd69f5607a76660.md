# 第 11 章：测试调试与质量改进

状态：`DESIGNED`；4 学时，模块分配为 1＋2＋1。以下为待执行实验，不能把预期结果复制成验收报告。

## 进入条件与学习目标

已完成监测、角色、演练和责任模块，能从日志定位一次请求。教师须先制作隔离 MySQL 环境、可重复种子、并发协调模板和仅测试环境生效的时间线失败注入点；这些资源当前尚未随文稿交付。

完成后，学生能从业务风险选择测试层级；用真实数据库证明并发冲突和事务回滚；根据复现证据提出最小修复；区分“测试通过”“未执行”“环境阻塞”和“未覆盖”。

## 模块一：把验收标准变成测试计划（1 学时）

测试不是让 AI 给自己生成的代码打分。先从需求写可观察预期，再选择单元、接口集成、浏览器检查，避免所有用例都只测成功。

| 风险 | 合适的验证方式 | 关键预期 |
| --- | --- | --- |
| 有效零被当作缺失 | 前端函数/组件测试 | 0 显示为有效值，null 显示未知 |
| 关闭条件缺失 | 服务单元＋接口集成 | 逐项缺条件均拒绝 |
| 越权写入 | 带实际角色的接口请求 | 本人范围外或查看者返回 403 |
| 同版本相互覆盖 | 真实 MySQL 并发请求 | 一次成功，一次 409 |
| 主记录更新、历史失败 | 真实 MySQL 故障注入 | 两者均不提交 |
| 刷新或网络失败 | 浏览器检查 | 数据不伪造成功，提示可理解 |

各组挑选一条高风险需求，先写“给定—当—则”用例和失败证据格式。Mock 可用于隔离纯业务分支，不能证明真实数据库锁、唯一约束或事务行为。

## 模块二：执行并发、回滚与缺陷修复（2 学时）

所有写操作限定教师预备的独立测试库；确认库标识后才执行。保留执行时间、代码版本、种子版本、请求、响应及查询结果，日志中不保存口令或完整令牌。

最小实验 A——同版本并发：

1. 准备一条版本为 n 的责任记录及两个有效候选人员，记录主行和时间线基线。
2. 两个独立请求均携带 `expectedVersion=n`，分别申请改为 A、B。用教师并发模板的屏障统一释放，不以先后点击代替并发。
3. 等待两个请求完成。预期一个成功、一个 HTTP 409 `VERSION_CONFLICT`；请求完成顺序不预设。
4. 使用新连接回读 MySQL：最终 owner 与成功请求一致，version 为 n＋1，新增且仅新增一条对应时间线。若两次都成功，检查锁和版本比较是否在同一事务。

最小实验 B——事务整体回滚：

1. 分别记录一条事件和一条责任记录的版本、字段与历史行数。
2. 在真实数据访问路径中启用教师测试注入点：主记录更新后、提交前，让时间线插入抛出可识别异常；不得 mock 掉数据库访问。
3. 各发起一次合法修改，确认接口未返回成功。事务结束后用独立新连接查询，字段、版本和历史行数都应等于各自基线。
4. 关闭注入点，再执行一次正常修改，确认主行和时间线同时增加。不要让测试框架最外层的自动回滚掩盖业务事务错误；模板须验证请求事务结束后的持久状态。

最小实验 C——从缺陷到回归：

选择一条实际失败或教师预置缺陷，先固定复现，再把最少的代码、请求和日志交给 AI；检查它的因果解释，人工实施最小修改，重跑失败用例和受影响用例。记录修复前后证据，不把“AI 说修好了”当作结果。

产出：测试矩阵、两类真实数据库证据、一个缺陷修复记录。环境未就绪时标记“阻塞”，说明缺少资源；不能用内存数据库或预填截图换取本章完成。

## 模块三：交叉审查与回归结论（1 学时）

两组交换证据，审查请求版本、数据库名称、结果时间及代码版本能否对应，检查是否遗漏失败分支、是否只截取最后一行成功输出。每人现场解释一个测试为何能发现错误、还不能证明什么。

教师按风险复核真实数据库实验。单元通过、集成通过和浏览器通过分别报告，不汇总成没有范围的“全部通过”。

## 典型问题、巩固与接力

并发结果不稳定：检查两个请求是否真用同一版本及协调是否生效。查询看见未提交数据：检查是否复用了业务连接。回滚测试永远通过：检查测试外层事务和异常是否在提交后才注入。偶发失败被重复运行掩盖：保留首次失败，查清随机种子、时钟和共享数据污染。

课后补一条边界或异常测试，并说明它对应的需求。进阶可统计覆盖率帮助找遗漏，但不以百分比替代业务证据。
