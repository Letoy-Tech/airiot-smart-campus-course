# 第 03 章 架构、数据与接口设计

> 本章为教材初稿，图、类名与 JSON 是教学设计和静态样例，不是已实现工程。`CampusDataProvider`、`TeachingMockProvider`、`AiriotProvider` 为待实现名称。课内 4 学时，按 1＋2＋1 安排；数据库、并发和 API 均待后续实测。

## 为什么同一个字段会让两个人都“没有写错”

小林准备写设备页面，认为后端会返回一个设备数组；小周准备写接口，返回的却是带 `code`、`message`、`data` 的对象。两人分别检查自己的片段，都觉得有道理，放在一起后页面却显示空白。另一个组把 `online` 写成字符串“正常”，随后发现无法表达未知。

这些问题不一定需要更多代码，而需要在两端开始实现前约定数据形状、含义和失败行为。接口合同就是这种约定。架构说明职责，数据模型说明哪些事实要保存，接口合同说明双方如何交换事实。本章先完成一条设备读取的设计；事件与数据库图用来预览后续问题。

## 进入条件与学习目标

准备第02章R01的三个情境，先查[教学接口约定](../contracts/教学接口约定.md)的通用约定、核心读取对象及夹具基线。本章用纸笔和文本即可完成；方法签名、迁移和种子仍由教师在资源制作阶段冻结。

完成后，你应能沿一次读取说明前后端与数据源的责任；辨认 HTTP 请求和 JSON 响应；从外层对象找到设备数组；核对 ID、空值和时间；把一空间两设备的读合同交给下一章使用。ER、状态机和事务本章只预览，详细设计与实现分别留给第09—11章。

### 3.2 数据源端口为什么不是“随便换一个网址”

端口在这里指业务需要的读取能力，而不是 TCP 端口号。`CampusDataProvider` 计划暴露空间、设备、最新点值、历史、原始报警、接入状态六项读取能力。业务服务依赖这些能力，具体提供器负责把模拟数据或上游数据整理成合同要求的形式。

模拟提供器使用确定性种子和可控时钟。相同种子、相同时钟与相同故障设置，应便于得到可核对的数据，学生才能解释为什么某点过期。真实提供器失败时必须报相应错误，不能静默返回模拟成功；否则页面可能继续变动，却隐藏了真正的接入失败。

`source="TEACHING_MOCK"` 表示数据来自教学模拟提供器，`source="AIRIOT"` 表示来自真实适配路径。`simulated=true` 仍独立存在：AIRIOT 中的模拟设备也必须保留这个标志。来源不等于真实性，两者都要在设计中有位置。认证基础由教师预制，学生负责业务授权，不能把“教师提供登录”误解为“业务请求已经自动安全”。

## 模块二：把业务事实变成数据与 API（2 学时）

### 3.3 先读懂一次 HTTP 请求与 JSON 响应

HTTP 是浏览器与服务交换请求、响应的一套规则。`GET /campus/devices` 中，GET 表示读取方法，后面是后端路径，不是本机文件名。完整访问地址还包含协议、主机和端口，例如 `http://<本机主机>:<教学端口>/campus/devices`；尖括号必须由未来资源说明替换，不是现在可以访问的地址。本次GET没有请求体；后面学习POST时，才会在请求体中传入要提交的数据。

响应先有HTTP状态，例如200表示本次请求成功处理；随后是内容。JSON是一种文本数据格式：`{}`包住对象，`[]`包住数组，键名与字符串用双引号，数字、true、false、null不加引号。`null`表示这里没有值，不是字符串`"null"`。

先预测下面片段中第一台设备的名称，再逐层核对。片段为了读语法只保留少数字段，完整接口样例在3.5节。

```json
{"code":0,"message":"ok","data":{"items":[{"name":"教学温度设备","online":true}],"observedAt":1792281600000}}
```

| 逐层读取 | 得到什么 |
| --- | --- |
| 响应外层对象 | code、message和data三个键 |
| `data` | 装着列表和观察时间的对象 |
| `data.items` | 设备数组，不是外层对象本身 |
| `data.items[0]` | 第一条设备；数组下标从0开始 |
| `data.items[0].name` | 字符串“教学温度设备” |

若用变量`response`保存外层对象，代码中的完整取值是`response.data.items[0].name`。先确认数组非空，才能取第一条；`items:[]`是成功的空列表，读取失败则没有这份成功结果。课内先能说明这两个差别，不必立即记住框架请求库的写法。

### 3.4 DTO、数据库记录和页面模型解决不同问题

DTO 是双方交换数据的形状。Device DTO 包含设备名称、分类、通信状态等前端需要的字段；它不应直接暴露数据库用户实体或上游秘密。数据库记录则服务持久化和约束，可能采用不同列名与表结构。页面模型还可以增加展开、选中等交互状态，这些状态不必写回设备对象。

例如，空间的 `buildingId` 可以为空，因为本地映射还没建立。前端可以显示“未绑定楼栋”，不能为了方便渲染就写一个不存在的楼栋 ID。设备名称是显示内容，设备 ID 才是关联依据；两个设备同名时，按名称保存责任关系会产生歧义。

先用字段字典回答类型、是否可空和来源，再写 JSON：

| 字段或对象 | 类型与含义 | 设计时特别检查 |
| --- | --- | --- |
| `Device.online` | `boolean \| null`，通信三态 | 字符串和数字不是三态成员 |
| `Device.communicationTime` | `number \| null`，epoch 毫秒 | 不用请求时间补成通信时间 |
| `observedAt` | 后端本次观察时间，epoch 毫秒 | 不是每个点的采样时间 |
| `Device.id/spaceId` | 设备标识与所属空间标识 | 按ID关联，不用名称猜测关系 |

epoch毫秒表示从约定的1970年时间起点累计的毫秒数，是传输格式，不是给使用者直接阅读的日期。本章保留原数值，不手算日期。通信时间是设备通信的源时间，observedAt是后端组织本次读取的观察时间，二者不能互相填补；采集点的质量和单位在第07章继续展开。

### 3.5 一空间、两设备的最小读合同

首次贯通使用 `GET /campus/spaces` 和 `GET /campus/devices`，成功外层为 `{code:0,message,data}`，列表位于 `data.items`。接口须在教学认证之后访问。下面为静态样例，时间只是固定的 epoch 毫秒输入，不是本次运行产生的记录；`tableId` 与标签的示例取值仍须由教师种子包冻结。

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "items": [
      {
        "id": "teaching_space_01",
        "name": "教学空间一",
        "type": "room",
        "campusId": null,
        "buildingId": null,
        "floor": null
      }
    ],
    "observedAt": 1792281600000
  }
}
```

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "items": [
      {
        "id": "teaching_env_01",
        "tableId": "teaching_environment",
        "name": "教学温度设备",
        "category": "environment",
        "spaceId": "teaching_space_01",
        "spaceName": "教学空间一",
        "online": true,
        "communicationTime": 1792281598000,
        "simulated": true,
        "switchOn": null,
        "tags": [{"id": "temperature", "name": "温度", "unit": "°C"}]
      },
      {
        "id": "teaching_energy_01",
        "tableId": "teaching_energy",
        "name": "教学功率设备",
        "category": "energy",
        "spaceId": "teaching_space_01",
        "spaceName": "教学空间一",
        "online": null,
        "communicationTime": null,
        "simulated": true,
        "switchOn": null,

```

`switchOn:null` 是保留合同字段，并非要求制作控制按钮。基础教学的 `canControl` 对所有角色均为 `false`。`category` 固定为 environment、energy、facility、lighting 四类，不用中文显示名替代传输值。界面可以翻译显示文字，但请求与响应仍使用约定枚举。

这两个列表响应保留参考合同的形状，没有自行加入 `source`。概览和历史合同明确携带 `source`，数据提供器和教学运行配置也显式选择来源。最小台账可以根据教师确认的教学配置显示“教学模拟”；若需要跨来源的统一列表 DTO，应先协调合同，再同步前后端和测试，不能每章各自加一个字段。

## 模块三：用样例评审合同（1 学时）

### 3.7 合同除了成功 JSON 还要写失败行为

HTTP状态和JSON中的业务码是两层判断：拿到200还要确认内容是约定JSON及code=0。读取返回401表示身份无效，403表示没有读取权限；数据源故障按合同转为502/503，不能让使用者误以为需要重新登录。完整错误码表供查阅，不要求本章背诵。

用第02章R01的三个情境审查自己的读合同：

| 已给出的响应或现象 | 纸面预期 | 人工核对 |
| --- | --- | --- |
| code=0且items含两条记录 | 显示两条；null显示未知 | 名称取自哪一层？实际数量是多少？ |
| code=0且items为空数组 | 显示暂无设备 | 有没有误把空结果标成请求失败？ |
| 没有取得成功JSON | 显示不可用，保留适用的旧快照与旧时间 | 有没有凭空补两条数据或宣称数量为零？ |

再看一个故意构造的错误片段`"online":"false"`。先判断它与合法false有何不同，再解释为什么应报告数据合同问题，不能强制转换成“离线”。这是纸面反例，不是本章新建一个错误接口。

### 3.8 让前后端角色只靠合同交流

一人扮演前端，另一人扮演后端。前端同学只看文档，说出请求路径、数组位置和三种结果；后端同学说出读取身份、提供器和返回字段。把必须口头补充的条件写进本组读合同。此轮没有持久化写入，不要求演练事件动作。

用以下提示辅助评审，不把模型建议直接当共同合同的新版本：

```text
本次只审查GET /campus/spaces和GET /campus/devices的读取合同。
外层为{code:0,message,data}，数组在data.items，时间为epoch毫秒。
online只能为true/false/null；教学设备simulated=true。
不自行给列表增加source，来源显示遵循本章确认的教学配置。
请检查ID关联、字段类型、空数组和读取失败的区别，
再指出第一台设备名称的准确取值路径。
只输出“位置、冲突、影响、修订建议”，不要生成实现代码，
不要扩展事件写入、控制或通知，也不要声称已经调用了接口。
我的材料：[粘贴相关内容；长文件按编号分段]
```

审查时重点看取值层级、null语义和范围是否正确。若确需改变共用字段，先列出受影响类型和测试，再由共同维护者统一修订；本组的阅读笔记不能单方面改变全课程合同。

## 最小实验与验收

1. 在给定架构图旁写出设备读取经过的三个部分，不从空白重画架构。
2. 复制完整的空间和设备JSON到本组读合同，标注两个设备的spaceId对应哪条空间。
3. 先写出第一台名称的取值路径，再核对答案；为online、communicationTime、observedAt补类型与含义。
4. 对照R01的正常、空数组、失败三情境检查显示预期，任选一处请AI审查并记录人工判断。
5. 同伴只看合同复述读取过程，补齐缺口后停止。本章不要求提交ER图、事件请求、SQL或并发实验。

| 常见错误 | 判断方法 | 修订方向 |
| --- | --- | --- |

## 课后练习与答案要点

任选一题巩固即可；第3、4题随图作为后续预告，不是本章课内考核锁与事务的要求。

**练习一。** AIRIOT 返回一台模拟设备，`source` 与 `simulated` 应怎样表达？  
答案要点：在承载来源的响应中 `source="AIRIOT"`，对象仍保留 `simulated=true`。不能把来源标成教学模拟，也不能因上游名称而取消模拟标识。

**练习二。** 为什么 Device DTO 不应直接复用数据库用户实体？  
答案要点：职责、字段和保密边界不同。DTO 应明确列出所需设备字段，不携带账户凭据或与客户端无关的内部字段。

**练习三。** 两个请求同带版本 3，为什么只比较客户端数字还不够？  
答案要点：必须以数据库当前记录为依据，并保证检查和修改的并发控制。本方案在事务中锁定记录，比对版本并原子保存主记录与时间线，随后用真实并发测试验证。

**练习四。** 时间线插入失败，主记录版本已经加一，这能算成功吗？  
答案要点：不能。若确实持久化了这个状态，说明原子性目标未实现；应回滚主记录并修复事务边界。纸面承诺不能充当回滚证据。

**练习五。** 页面请求未知值时收到 `null`，把它改成零能否减少前端判断？  
答案要点：会伪造测量事实。应在显示层明确未知或缺失，保留真实零值；质量、单位和时间也应保留。

进阶选做：给数据源端口写一页伪接口说明，只列六项读取能力、输入和错误，不固化尚未制作的 Java 方法签名。比较模拟与 AIRIOT 实现怎样满足同一合同，不尝试真实控制或写入。
